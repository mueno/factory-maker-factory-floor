# Factory Maker UX刷新評価 — Agent Experience・共同作業・回復性

## ① 結論

**首位はC「Evidence Trail」85点、次点はE「Agent Glass」83点**です。

Cは、依頼から検証までの流れ、担当者、revision、証拠、人の確認を一本の線で読めます。3分のデモで「人とエージェントが何を共同で完成させたか」を説明しやすい点が決め手です。Eは、同じ成果物のrevision、実行中のツール、READ/WRITE、実行結果、Undo、人の承認権限を最も具体的に示しています。ただし、初回の依頼から完了までの物語が画面にないため、単体では次点としました。

推奨する実装方向は、**Cの証拠線を画面の骨格にし、Eのライブ操作パネルを現在工程へ組み込む構成**です。

## ② 評価方法と前提

本評価人格は、Ilya Grigorik氏、Jude Gao氏、Sean Roberts氏の公開された技術関心を、Agent Experience、共同作業、回復性という観点で統合した**近似的な評価レンズ**です。実在する各氏の内面、実際の採点、投票行動を示すものではありません。

5枚のボードを原寸で確認し、画面から確認できない挙動は加点していません。また、次の注目点は新しい配点軸を追加せず、指定された5基準の中で評価しました。

- 人とエージェントが同じライブ状態を見ているか
- 変更内容、実行ツール、結果を観測できるか
- 人が重要判断を保持し、不要な確認で作業を止めないか
- 現在の工程で使えるツールを発見できるか
- 失敗、再試行、取消し、revision復元が正常な経路として見えるか
- 3分で依頼から完了までを一本の物語として示せるか

## ④ 各案の評価

### A. Shared Canvas — 72点

- **強み:** 成果物を最大面積で表示し、`HUMAN`と`AGENT`の変更履歴を分離しています。入力欄も一つで、モバイルでも成果物と履歴の関係を保っています。
- **致命的リスク:** 利用可能なSite Tool、入出力、revision、実行結果、失敗時の操作が見えません。このままでは通常の共同編集画面でも成立し、エージェントが人の修正を読み直したか検証できません。
- **実装に残す要素:** 成果物中心のキャンバス、人とエージェントの名義分離、成果物の近くに置く短い変更履歴。

### B. Command Studio — 69点

- **強み:** 一つの依頼、ライブプレビュー、工程表示、`Approve direction`が一画面に収まり、短時間のデモを始めやすい構成です。進行中の状態も一目で分かります。
- **致命的リスク:** 依頼欄と応答表示が通常のAIアプリビルダーに近く、同じページ状態をツールが直接更新するWebMCP固有の効果を確認できません。変更履歴、ツール発見、revision競合、Undo、再試行もありません。
- **実装に残す要素:** 単一の開始欄、生成中も操作対象を見失わないライブプレビュー、重要判断に限定した一つの主要ボタン、軽量な工程表示。

### C. Evidence Trail — 85点

- **強み:** `REQUEST → CONCEPT → BUILD → VERIFIED`の線上に人とエージェントの担当、完了状態、revisionを置き、現在の`Rev. 3`を成果物、証拠、人のレビューへ結び付けています。3分で開始から完了までを説明する骨格として最も強い案です。
- **致命的リスク:** `TOOLS USED`が名称のないアイコンだけで、現在使えるツールと実行済みツールを区別できません。version一覧も閲覧に留まり、失敗した操作、無変更の拒否、再試行、revision復元が操作として見えません。ここを実装しなければ「証拠を後から眺める画面」で止まります。
- **実装に残す要素:** 工程を貫く証拠線、actorとrevisionの併記、成果物と検証項目の同時表示、人専用の最終レビュー、モバイルでの縦方向の再構成。

### D. Calm Launchpad — 58点

- **強み:** 初回表示の依頼欄と主要操作が明確で、専門知識がなくても開始できます。次工程を折りたたむ設計は、モバイルでも認知負荷を抑えます。
- **致命的リスク:** 画面にあるのは依頼、提案、`Review & continue`までです。共有revision、変更者、Site Tool、実行結果、失敗、Undoがなく、通常の段階式ウィザードとの差を示せません。完了までの共同作業も一枚から追えません。
- **実装に残す要素:** 最初の10秒に使う単一の依頼欄、段階的開示、モバイルの縦方向レイアウト。D全体ではなく、Cの開始状態として採用するのが妥当です。

### E. Agent Glass — 83点

- **強み:** `Shared artifact`の`Revision 12`、`Agent active`、現在の`WRITE`操作、`Success`、後続のREADツール、人専用の`Approve`と`Undo`が同じ画面にあります。同じライブ状態、観測可能性、制御可能性、ツール発見性を最も明瞭に表現しています。
- **致命的リスク:** 初回の利用目的と、依頼から検証・公開までの進行が見えません。OpenAPI仕様を中心にした技術的な画面は、初見の非開発者に「最初に何をすればよいか」を伝えにくく、成功例しかないため失敗からの回復能力も実証できません。
- **実装に残す要素:** 現在のツールと後続ツールの一覧、READ/WRITE表示、revisionと実行結果、人専用の承認領域、Undo。Eの全面的なコックピットではなく、Cの現在工程パネルとして使うのが適切です。

## ⑤ 推奨案と次の一手

実装は次の一案へ収束させることを推奨します。

1. Dの単一依頼欄から開始する。
2. 依頼を受けた時点で、Cの証拠線を開き、`Human / Request / Rev. 1`を記録する。
3. 人が内容を修正したら、新しいrevisionを作り、エージェントがそのrevisionを読み直したことを画面と戻り値の両方へ表示する。
4. Cの現在工程内にEのパネルを置き、利用可能なツール名、READ/WRITE、実行中・成功・失敗、入力revision、出力revisionを表示する。
5. 確認は企画採用、仕様固定、公開だけに限定する。読み取りや安全な下書きでは人を待たせない。
6. デモでは意図的に古いrevisionを書き込み、状態が変わらない拒否、原因、`Retry with Rev. n`、Undoまたはrevision復元までを示す。
7. 最後にCの`VERIFIED`へ到達し、成果物、ツール戻り値、画面状態、証拠が同じrevisionで一致していることを人が確認する。

この構成なら、入口の分かりやすさ、共同作業の物語、WebMCP固有の操作、失敗回復を3分の中で一続きにできます。
