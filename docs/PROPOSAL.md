## 1. エレベーターピッチ

**Adlib は「アプリが存在しない状態から、ユーザーの操作に応じてUIが即興生成される」Webランタイム。**

Runway Solaris が示した「モデル自体がアプリケーションである」体験を、ピクセルのフレーム生成ではなく **DOM生成** で再現する。頭脳（LLM）はアプリに同梱せず、**WebMCP（`document.modelContext`）でページがツールを公開し、ユーザー自身のブラウザエージェント（Gemini in Chrome / Copilot / Claude in Chrome 等）が UI を即興で描く**。

> ユーザー「経費precheckのミニアプリ出して」
> → エージェントが Adlib のツールを呼び、フォームUIがその場に出現
> → ユーザーが生成されたボタンをクリック
> → 次の画面・挙動もその場で即興生成される（事前にコードは1行も書かれていない）

## 2. 背景

### 2.1 Solaris が示したパラダイム

2026-08-31、Runway が Interface World Model「Solaris」を発表。UIのレンダリングとインタラクション応答を単一モデルがフレーム単位で生成する。ただし:

- サーバーGPUクラスタ前提・非公開（パートナー限定）
- ピクセル生成のため文字が不安定、コピペ・アクセシビリティ・IMEが本物でない
- 実行コストが極端に高い

### 2.2 DOM生成アプローチの優位性

UIはゲームと違い**離散的なインタラクション**の連続であり、24fpsのフレーム生成は不要。「操作→次のUI状態」を DOM として生成すれば:

- テキストは常に鮮明、フォーム・IME・コピペ・スクリーンリーダーが本物として機能する
- 1操作あたり数百ms〜2秒の応答で体験が成立する
- 生成物がHTMLなので検査・サニタイズ・永続化が可能

### 2.3 WebMCP の登場（2026年の追い風）

- Chrome 149 でパブリックオリジントライアル開始（2026-05、Google I/O。〜Chrome 156 予定）
- ページが `document.modelContext.registerTool()` で型付きツールを公開し、ブラウザ常駐エージェントが直接呼び出せる標準
- 仕様は流動的（2026-07 ドラフトで `navigator.modelContext` → `document.modelContext` へ移動、Chrome 150 で旧APIは非推奨）
- Microsoft Edge も同系APIを推進、W3C Web Machine Learning CG で標準化議論中

つまり**「ページがエージェントに操作面を差し出す」インフラがブラウザに載り始めた最初の年**であり、これを本格活用したショーケースはまだほぼ存在しない。

## 3. 目的とゴール

### 目的

1. Solaris型「即興ソフトウェア」体験を、現実的なコストとWeb標準技術で成立させる
2. WebMCP の実戦ノウハウ（ツール設計・セキュリティ・デバッグ）を先行獲得し、既存プロダクト（規定チェッカー等）への横展開資産にする

### ゴール（本フェーズ）

- G1: プロンプトから任意のミニアプリUIが立ち上がり、生成UIへの直接操作に対して即興で次状態が返る（往復 P50 ≤ 1.5s）
- G2: WebMCP 対応ブラウザでは **APIキーなし**（ユーザーのエージェントが頭脳）で動作する
- G3: 非対応ブラウザでも Direct API フォールバックで同一体験が動く
- G4: 公開デモとして安全（生成UIのサンドボックス化、プロンプトインジェクション対策、キー非露出）

### 非ゴール

- ピクセル/フレーム生成（world model の自作・ホスティング）はしない
- 生成UIの永続的な「アプリ書き出し」（コードエクスポート）は本フェーズではしない（将来候補）
- ヘッドレス自動化は対象外（WebMCP自体が human-in-the-loop 前提）

## 4. ターゲットとユースケース

| ペルソナ | ユースケース | 価値 |
|---|---|---|
| 一般ユーザー（ブラウザエージェント利用者） | 「その場アプリ」: 割り勘計算、タイマー、簡易家計簿、意思決定マトリクス等を会話で出す | インストール不要・目的特化UIが数秒で手に入る |
| 開発者・デザイナー | インタラクション付きプロトタイピング。「触れるワイヤーフレーム」を会話で反復 | Figma以前の発散フェーズを高速化 |
| WebMCP に関心のある技術者 | ツール設計・エージェント連携の参考実装 | 標準の実戦例として希少 |
| AllNew 社内 | 規定チェッカー等へのWebMCP適用の予行演習 | 「自社サイトをエージェント対応させる」知見 |

## 5. 提供価値と差別化

| 比較対象 | Adlib の差別化 |
|---|---|
| Runway Solaris | ブラウザだけで動く / 文字・フォーム・a11yが本物 / 運用コストほぼゼロ（BYOA） / 今日公開できる |
| websim 等の生成サイト系 | 「1回生成して終わり」ではなく**操作ごとの継続即興**が主役。挙動もその場でモデルが決める |
| Imagine with Claude 型デモ | 特定ベンダーのクローズド環境ではなく、**WebMCP標準の上でエージェント非依存**（Gemini/Copilot/Claude いずれでも頭脳になれる） |
| 通常のAIアプリビルダー（v0等） | コードを「書いて配布する」のではなく「実行時に即興する」。ビルド工程が存在しない |

**キーコンセプト: BYOA（Bring Your Own Agent）** — 頭脳をユーザー側が持ち込むため、運営側の推論コストがゼロでスケールする。WebMCP時代の新しい配布モデルの実証になる。

## 6. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| WebMCP仕様の変動（API名・形状） | 中 | `document.modelContext ?? navigator.modelContext` の互換ラッパー1点に隔離。OT期間（Chrome 149–156）を明記し追従 |
| エージェント側の実装差・ツール呼び出し品質 | 高 | ツール数を最小（5個以下）に絞り、description を丁寧に書く。Direct API モードを常備し体験を保証 |
| ページからエージェントを起動できない（現仕様は agent→page 方向のみ） | 高 | 設計書 §5.3 の3段構え（イベントキュー + 継続指示 / Direct API 委譲 / 将来仕様待ち）。**直接操作ループの主経路は当面 Direct API** と割り切る |
| 生成UI経由のXSS・プロンプトインジェクション | 高 | 生成UIはJS禁止・宣言的 `data-action` のみ。DOMPurify allowlist + sandboxed iframe + CSP。詳細は設計書 §8 |
| Direct API モードのキー管理・コスト | 中 | キーはエッジプロキシのサーバー側のみ（クライアント非露出）。レート制限・オリジン検査。デモはターン数上限 |
| 生成品質（壊れたHTML・迷走する挙動） | 中 | スキーマ検証 + 修復リトライ（最大2回）+ 「前状態へ戻す」Undoを常設 |

## 7. 成功指標（KPI）

- 操作→UI反映レイテンシ: P50 ≤ 1.5s / P95 ≤ 4s（Direct APIモード・高速モデル時）
- 台本タスク完遂率: 代表10シナリオ（割り勘・タイマー・カンバン等）で 8/10 以上が人手介入なしで完遂
- ツール呼び出しエラー率: < 5%（スキーマ不一致・サニタイズ全落ち含む）
- WebMCPモード実働: 対応ブラウザ + エージェントで E2E デモが再現可能であること（動画証跡）
